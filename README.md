# 楚河论弈 · 中国象棋模型竞技场

让两个大模型隔河对坐、实时对弈的中国象棋 Web 应用。红黑双方可以分别接入不同的模型与 API Key，后端负责棋规裁判、局面推送和模型调度，前端以中国象棋棋盘实时直播整盘棋。另有四个独立页面：**模型库** 可保存、编辑和删除可复用的模型配置；**自动评测** 可让多种模型配置两两循环对弈并生成积分排名；**锦标赛** 先让 10 个入围赛模型分两组单循环、每组前二进入四号种子池，再把 16 个模型分入四个种子池、抽签分组并进行小组单循环与 6 局 3 分制淘汰赛，支持断电/重启后的断点续赛，并为每一届赛事保存完整档案；**对局管理** 可检索、调阅和清理历史对局档案，也可以在「锦标赛档案」中回看每一届锦标赛的小组积分、淘汰赛对局图与系列赛比分。自动评测或锦标赛进行中时，可从赛事页一键跳到棋盘观战；对局档案详情内还能直接在棋盘上逐手回放整局棋谱。

## 功能

- 红、黑双方独立配置：OpenAI Chat Completions 兼容接口或 Anthropic Messages 接口。
- **顶部固定页签**：棋盘、自动评测、锦标赛、模型库、对局管理五个入口固定在界面顶部横向排列，随时可切换；手机端自动压缩，当前页面高亮。
- **模型库**（独立页面 `/models`）：把模型名称、接口协议、模型 ID、Base URL、API Key、默认思考强度与推理参数开关保存为对象，支持新增、编辑和删除；每个对象可直接测试接口、模型 ID 与密钥是否可用，并显示延迟、Token 与回复预览。观战棋桌、自动评测和锦标赛的每个模型位都可以直接选择已保存对象，也可临时自定义。
- 内置 DeepSeek、OpenAI、Anthropic、Moonshot、智谱、OpenRouter、Ollama 本地等预设，也可完全自定义 Base URL 与模型 ID。
- 每一步向模型提供当前 FEN、可视棋盘、将军状态、近期着法和完整合法着法列表。
- 红黑双方可分别设置 **思考强度**，影响推演要求、近期棋谱数量、理由长度与单步等待上限。所有采用 **OpenAI 协议**的模型都可以直接选择 OpenAI 兼容的 `minimal / low / medium / high` 档位，不依赖服务是否公开模型元数据，并**默认自动发送**对应的 `reasoning_effort`；模型卡和模型库仍支持 **“从 API 读取”** 拉取服务商提供的额外档位。对于只返回模型 ID、不暴露推理能力的 OpenAI 兼容网关（例如并行科技 `https://llmapi.paratera.com`），会额外发送一次极小的 `reasoning_effort` 探测请求确认推理输出；即使探测不到输出，也保留 OpenAI 兼容档位以供设置。
- 每方另有 **“发送 OpenAI 兼容推理参数”**（Anthropic 为“发送扩展思考参数”）开关：OpenAI 协议默认开启并自动发送 `reasoning_effort`，遇到不支持该参数的网关可手动关闭；Anthropic 默认关闭，开启后按扩展思考预算发送。
- 模型返回严格 JSON 着法；服务端二次校验，非法着法会带着合法列表反馈重试，绝不直接落子。
- 完整中国象棋规则：马腿、象眼、九宫、炮架、过河兵、将帅照面、将军、将死、困毙判负。
- **死局自动判定**：双方失去全部车马炮兵时立即判和；连续 60 回合无吃子且无兵卒推进也判死局。
- **自动终局**：每步落子后立即裁定将死、困毙或和棋；进入终局即停止全部模型请求、释放密钥并在前端锁定结果。
- SSE 实时推送，前端棋盘平滑走子、标记最后一步与被将军的将帅、记录棋谱和吃子。
- **棋盘观战**（`/watch`）：自动评测或锦标赛进行中时，赛事页会显示「查看棋盘」入口，跳到当前对局的实时棋盘。页面复用观战棋桌的棋盘、双方名牌、思考状态与棋谱；直达链接可指定 `mode` 与 `gameId`，不指定 `gameId` 时跟随当前对局，最近一局结束后仍保留终局棋盘。没有进行中的对局时显示空状态与返回入口。
- **棋局回放**：对局管理的详情面板内嵌只读棋盘，可逐手前进/后退、跳到首手/末手、自动播放、拖动进度条；点击下方棋谱中的任意一手会直接跳到该局面并高亮该行。
- 暂停/继续、重试本回合、重新布阵；模型连续给出无法解析或非法的着法时，直接判该方负，不再作为异常局跳过。
- **自动评测**（独立页面 `/tournament`）：可添加 2–8 个模型配置，所有组合两两循环对弈；每对可设 1–20 局，红黑轮换，奇数局会在不同对阵间轮换多出的一局执红。实时显示每个模型的胜 / 和 / 负、积分与排名，并可逐局查看结果；评测可随时终止，不影响观战中的棋桌。模型连续不给出合法着法的对局按对手胜计入积分；网络/鉴权等请求异常仍单列为异常局。
- **16 强锦标赛**（独立页面 `/championship`）：先进行 **入围赛**——10 个模型分入 A、B 两组（每组 5 人）组内单循环，每组前 2 名进入四号种子池；池一至池三仍由用户各配置 4 席，共 22 个参赛配置。之后把 16 位选手按四个种子池随机抽签分成 A–D 四组，每组各池 1 个模型；小组内单循环（每对一局，每人 3 局），前 2 名进入八强；八强赛、半决赛、决赛统一采用 **6 局 3 分制**：每局胜方得 1 分、和局双方各得 1 分，先到 3 分者晋级；若双方在同一局同时到 3 分（如三连和形成 3:3），此后先取胜的一方晋级；6 局封顶仍未分胜负时按小组排名裁决，若双方小组排名也完全相同则继续加赛至分出胜负。实时展示入围赛积分、小组积分、系列赛比分、完整对阵树与冠军。支持 **1–8 路并发**（默认 4）：入围赛按同轮无共享选手的波次并行，小组赛按三轮互不共享选手的批次并行，淘汰赛同轮系列赛并行，系列赛内部仍逐局进行。
- **锦标赛断电续赛**：每局结束后、手动中止、内部异常或服务关闭前都会把赛程、积分、系列赛比分和模型运行配置写入本机 `data/championship.json`。服务重启或断电后，页面会恢复“中断待续”状态，点击 **继续锦标赛** 即可从未完成处接着跑；已完成对局不会重赛，只有中断瞬间未结束的那一局会从第 1 手重新开始。手动中止和内部异常也可续赛；开始新一届会覆盖旧断点。
- **对局管理**（独立页面 `/admin`）：自动归档已结束的观战对局、自动评测对局和锦标赛对局，支持按来源、结果和模型关键词筛选，分页浏览，查看终局原因、双方模型配置、用时、Token 与完整中文棋谱；详情面板内可直接在棋盘上回放整局。可删除单条档案或清空全部。页面另设 **锦标赛档案** 视图：每届锦标赛（从小组赛第一轮到决赛）保存一份档案，可回看四个小组的积分排名、淘汰赛对局图、系列赛比分与逐局结果。档案写入服务端本地文件，重启后仍可查看。
- 临时填写的 API Key 只驻留浏览器表单与服务进程内存；模型库中的 Key 保存在本机 `data/models.json`，接口只返回掩码。Key 不进入 SSE、日志或历史档案；自动评测或锦标赛结束/终止时释放运行内存中的副本，但锦标赛断点文件需要模型配置与密钥才能续赛，因此会在本机 `data/championship.json` 中保留一份运行配置。
- 模型可用性测试会发起一次真实模型请求，可能产生少量 Token 费用；测试按当前配置发送推理参数，超时上限 30 秒，失败信息中的密钥会被脱敏。

## 快速开始

要求：Node.js ≥ 22.12（本项目在 Node 24 下开发）、npm。

```bash
npm install
npm run dev
```

打开 <http://127.0.0.1:4317>。

首次运行会自动创建本地数据目录 `data/`，用于保存模型库、历史对局、赛事断点与档案。该目录只存在于本机，已被 `.gitignore` 排除，不会上传到仓库。

生产模式：

```bash
npm run build
npm start
```

服务默认只监听 `127.0.0.1:4317`。需要换端口/地址时：

```powershell
$env:PORT=4400; npm start
$env:HOST="0.0.0.0"; npm start   # 公开监听前请先阅读安全说明
```

## 使用方式

1. 点击固定页签 **模型库** 保存常用模型配置（可选；也可以直接临时填写）；保存后或编辑时可点击 **测试可用性 / 测试连接** 验证接口、模型 ID 与密钥。
2. 在右侧“红方”和“黑方”的 **模型库** 下拉框中分别选择已保存模型；选择“临时配置（不保存）”则继续手动填写预设、Base URL、模型 ID 与 API Key。
3. 两侧可以是同一个模型，也可以是不同厂商的不同模型；本地 Ollama 等服务可留空 Key。
4. 选择本局思考强度：所有 OpenAI 协议模型都可直接选择 `minimal / low / medium / high`，并默认自动发送 `reasoning_effort`；也可点击 **从 API 读取** 拉取该模型服务商提供的额外档位。遇到不支持该参数的网关时，关闭“发送 OpenAI 兼容推理参数”即可只使用提示词策略。
5. 调整“落子间隔”和“最大尝试次数”，点击 **开局**。
6. 对局期间配置锁定；可以暂停、继续，请求层异常时可以重试本回合或重新布阵。若某方连续耗尽重试仍给不出可解析或合法的着法，该方直接判负，对手获胜。
7. 对局结束后可从棋谱查看结果，点击 **再来一局** 使用当前配置重新开始。

模型必须按提示返回：

```json
{"move":"h2e2","reason":"不超过当前思考强度限制的战略理由"}
```

其中 `move` 使用 UCCI 坐标。界面与提示词都会给出当前全部合法着法，模型只能从列表中选择。

### 模型库

点击固定页签 **模型库**，或打开 <http://127.0.0.1:4317/models>。该页面与对局、评测分离，只负责管理可复用的模型配置。

- 每个模型对象包含：名称、接口协议、模型 ID、Base URL、默认思考强度、API 推理参数开关和 API Key。
- 支持 **新增 / 编辑 / 删除 / 测试可用性**。编辑时可留空 API Key 保持原密钥，也可填写新 Key 替换或勾选“清除已保存密钥”。
- 模型卡上的 **测试** 按钮会使用已保存的接口、模型 ID、密钥和推理设置发送一次最小对话请求，最多等待 30 秒；结果显示可用/不可用、延迟、Token 与模型回复预览。编辑面板中的 **测试连接** 使用当前表单配置，可在保存前验证；编辑已有模型且密钥留空时复用已保存密钥。测试不会保存或修改配置，失败信息会脱敏，不包含 API Key。
- 在棋盘页的红黑双方、自动评测或锦标赛的每个参赛位，都可以从下拉框选择模型库对象；**锦标赛席位选择模型库对象后会自动采用模型库名称**，同一对象重复参赛时自动追加 2、3… 保持名称唯一。其他页面的参赛位名称仍可单独修改。
- 选择模型库对象后，接口协议、模型 ID 与 Base URL 锁定，思考强度与推理开关仍可分别覆盖；密钥由服务端在开局时读取，不返回浏览器。
- 删除模型对象不会影响已经开始的对局或评测；之后新的对局需要重新选择配置。
- 模型库默认保存在 `data/models.json`，已在 `.gitignore` 中排除。密钥以明文 JSON 保存在本机，接口只返回 `keyConfigured` 与末四位掩码；请妥善保护该文件，如需备份或迁移可直接复制。

编辑已有模型时也可以先测试当前表单配置，再决定是否保存：

测试结果按模型卡独立显示。

### 自动评测

点击固定页签 **自动评测**，或直接打开 <http://127.0.0.1:4317/tournament>。该页面与观战棋盘完全独立，使用单独的赛事调度器和 SSE 通道，不会改动正在进行的棋局。

1. 添加 2–8 个参赛位，为每个参赛位选择模型库对象，或填写临时的名称、协议、Base URL、模型 ID、思考强度与 API Key；同一个模型对象可以用不同思考强度重复参赛，只需参赛名称不同。
2. 设置 **每对模型的对局数**（1–20）。所有模型两两对阵；例如 3 个模型、每对 2 局，共 3 组对阵、6 局。
3. 点击 **开始评测**。服务端按对阵顺序逐局运行，复用观战棋桌的完整规则、提示词、非法着法重试、自动终局和单步超时；实时更新进度与积分榜。
4. 评测中可点击 **终止评测**：当前模型请求会被中止，未完成的对局标记为取消。评测结束后可修改配置重新开始。

计分与排名：

- 胜 = 3 分，平 = 1 分，负 = 0 分。
- 排名依次比较：积分 → 胜场 → 平局 → 报名顺序。
- 模型 API 异常导致的失败局单独计入“异常”，不参与胜平负和积分；这样可以避免把密钥失效或服务不可用误判成棋力差距。其余对局继续运行。
- 每对组合的红黑顺序逐局交替；对局数为奇数时，多出的一局执红资格会在不同组合之间轮换，尽量平衡先手。

> 自动评测会真实调用模型 API，模型数量 × 对局数越大，耗时和费用越高。每局最长可到 300 个半回合，建议先用每对 2 局验证配置，再扩大规模。

### 16 强锦标赛

点击固定页签 **锦标赛**，或打开 <http://127.0.0.1:4317/championship>。该页面拥有独立的赛事调度器和 SSE 通道，不会改动观战棋桌或自动评测。

页面先配置 22 个参赛席位：四号种子池页签中放置 10 位入围赛模型（A、B 两组各 5 席），运行入围赛后，每组前二自动进入四号种子池；池一至池三各 4 位直邀模型。

抽签完成后，页面会立即显示每组的小组赛积分与排名表，以及完整的淘汰赛对局图（八强签位先以 A1/B2 等种子占位，小组赛结束后填入实际出线模型）。开赛后会实时更新比分、积分和晋级路径。

1. 页面顶部为 **入围赛**：在四号种子池页签中配置 10 个模型，分入 A、B 两组（每组 5 席）。点击 **开始入围赛** 后，两组同时进行组内单循环：每对一局，每组 10 局、共 20 局，每人 4 局且红黑各 2 局。每组前 2 名晋级，同分依次比较：积分 → 相互对局积分 → 胜场 → 和局 → 席位顺序。四名晋级者自动填满 **四号种子池**，其余 6 位在入围赛阶段淘汰。
2. **种子池一至池三** 各固定 4 席，共 12 个直邀席位。用户把模型库对象或临时配置放入对应池，即完成种子池划分；从模型库选择对象时，席位名称会自动设为该模型库名称（重复时自动追加序号）。
   - **快速选择 4 个模型**：在池一至池三的任意池点击该按钮，从模型库勾选恰好 4 个模型并确认，即可一次性填满该池 4 席；按模型库列表顺序填入，会用选中模型覆盖本池原有 4 席，并自动带入库名称。
   - **入围赛快速选择 5 个模型**：A、B 两组各有一个「快速选择」按钮，从模型库勾选恰好 5 个模型即可一次性填满本组 5 席；已被其他席位占用的模型不会出现在候选中。
   - 也可以点击“用模型库填充空位”，按模型库顺序填入空席位（含入围赛席位）。
3. 入围赛完成后点击 **随机抽签**：四个种子池分别洗牌，再按池位组合成 A–D 四组，保证每组恰好拥有来自四个池的各 1 个模型。抽签后不能再手动改签；任何席位配置变化都会使抽签结果失效并要求重抽；若入围赛名单发生变化，则需重新发起入围赛。
4. 点击 **开始锦标赛** 后，服务端进行四组单循环小组赛：每组 4 人两两对弈一局，每人 3 局，每组 6 局，四组合计 24 局。红黑按赛程平衡；胜 3 分、和 1 分、负 0 分；请求层异常局单独计数，不计入积分；连续给不出合法着法的对局按对手胜计入积分。
5. 每组前 2 名出线。同分依次比较：积分 → 相互对局积分 → 胜场 → 和局 → 种子池位次 → 报名顺序。
6. 八强对阵为 A1–B2、C1–D2、B1–A2、D1–C2；半决赛由 QF1/QF2 与 QF3/QF4 的胜者组成，最后进行决赛。不设季军赛。
7. **淘汰赛统一为 6 局 3 分制**：每局胜方得 1 分，和局双方各得 1 分；先到 3 分的一方晋级。若双方在同一局同时到 3 分（前三局全平形成 3:3），进入加赛，此后先取胜的一方晋级。6 局封顶仍未分胜负时，按小组排名较高者晋级；排名比较顺序为小组名次 → 小组赛积分 → 胜场 → 和局 → 种子池位次。若以上全部相同，则继续加赛，直到出现一局胜负。
8. 淘汰赛红黑逐局轮换，排名较高者在第 1、3、5…局执红。赛事进行中可点击 **终止锦标赛**；当前请求会被中止，未完成的对局不再执行，且不会产生冠军。已中止、异常或中断的赛事同样会写入锦标赛档案，标注为未完成。
9. **断点续赛**：入围赛与锦标赛每完成一局都会分别写入本机断点文件 `data/qualifier.json` 与 `data/championship.json`，手动终止、内部异常和服务正常关闭前也会再次保存。服务重启或断电后打开页面，会看到“中断待续”状态和 **继续入围赛 / 继续锦标赛** 按钮；点击后从中断处继续，已完成的成绩全部保留，只有中断瞬间未结束的那一局会重赛。**开始新一届** 会覆盖旧断点。进程若在某一局进行中被强制杀死，最多损失这一局已走的棋，不会影响此前已归档的成绩。

入围赛 20 局，主赛小组赛 24 局，7 场淘汰赛系列赛每场最多 6 局，因此单届常规上限 **86 局**真实模型对局（入围赛 20 + 主赛 66）；若双方小组排名完全相同而触发加赛，实际局数可能继续增加。每局最长可到 300 个半回合，API 费用和耗时可能非常高；建议先用少量模型或本地服务验证配置。

### 历史对局管理

点击固定页签 **对局管理**，或打开 <http://127.0.0.1:4317/admin>。页面顶部可在 **对局档案** 与 **锦标赛档案** 之间切换。

- 服务端会把观战棋桌中正常结束的对局，以及自动评测、锦标赛中完成或异常的对局写入本地档案；重启服务后仍可查看。终止评测/锦标赛时尚未完成的对局不会被归档。
- 对局档案按单局检索；锦标赛档案按「一届锦标赛」建档，记录从小组赛第一轮到决赛的赛程快照。
- 每届锦标赛完赛、手动中止、内部异常或中断后都会更新一份档案；点击档案可回看冠军与晋级路径、四个小组的积分排名、淘汰赛对局图、每场系列赛的比分与逐局结果。未完成的档案会标注「已中止 / 异常中止 / 中断未续」。
- 支持按来源（手动对弈 / 自动评测 / 锦标赛）、结果（已完成 / 异常）过滤，并按模型名称或 ID、终局文案、错误信息搜索；每页 20 条。
- 点击任意记录可打开详情：双方模型与思考强度、胜负与终局原因、起止时间、用时、Token 统计、自动评测组次或锦标赛小组/系列赛信息，以及完整着法列表（中文记谱、UCCI、落子理由、单步用时和 Token）。
- 可删除单条档案，或清空全部档案；操作前会二次确认。删除只影响本地档案，不影响正在进行的棋局或评测。
- 档案默认保存在 `data/history.jsonl`（JSON Lines，每行一条对局）；每届锦标赛的完整档案保存在 `data/championships.json`（JSON 数组，按赛事去重更新）。两者均已在 `.gitignore` 中排除。对局档案只包含公开模型信息、结果和棋谱，锦标赛档案只包含公开模型信息、积分与对局结果，均不包含 API Key。需要备份或迁移时，直接复制这些文件即可。

### 思考强度与 API 推理参数

红黑双方、每个参赛位都可以独立设置思考强度，互不影响。模型卡和模型库编辑器中提供 **“从 API 读取”** 按钮；所有 OpenAI 协议模型无论是否读取成功，档位选择器都固定提供 OpenAI 兼容档位：

- **Ollama**：调用原生 `POST /api/show`，读取 `thinking.values` 与 `thinking.default`，例如 `low / medium / high`，也支持 `on / off` 等布尔档位。
- **OpenRouter / 带元数据的 OpenAI 兼容服务**：读取 `/models` 目录中的 `reasoning.supported_efforts`、`default_effort`、`thinking.values` 或 `thinking_levels` 等字段。
- **只有模型列表、没有推理元数据的 OpenAI 兼容服务**（例如并行科技 LiteLLM 网关）：模型目录只返回模型 ID，此时服务端会发送一次极小的 `reasoning_effort: medium` 请求，检测响应中的 `reasoning_content` 或 `usage.completion_tokens_details.reasoning_tokens`；检测到模型确实产生推理输出后，标注为已确认并继续提供通用档位 `minimal / low / medium / high`。该探测请求会产生少量 Token 费用，且不会写入对局或历史档案。
- **Anthropic 或未暴露思考元数据的服务**：回退到内置三档，并提示“未能从 API 读取”；不影响正常对弈。OpenAI 协议模型不回退到内置名称，始终保留 OpenAI 兼容档位。
- 读取到的档位会随模型库对象保存，下次选择该对象时直接复用；也可再次读取覆盖。自定义临时配置的档位只在当前页面保留。
- 读取请求只用于查询模型服务元数据，API Key 不会写入返回结果、SSE、历史档案或日志。

不同 API 档位会映射到同一套推演语义，因此内置三档仍作为回退与语义基准：

| 语义档位 | 典型 API 值 | 推演要求 | 近期棋谱 | reason 上限 | 单步等待上限 |
|---|---|---|---|---|---|
| 快速 | `quick` / `minimal` / `low` / `off` | 快速筛选稳健着法，不做长链推演 | 6 手 | 30 字 | 60 秒 |
| 标准 | `balanced` / `medium` | 比较若干候选着法，检查攻防 | 10 手 | 60 字 | 120 秒 |
| 深思 | `deep` / `high` / `xhigh` / `max` / `on` | 至少比较三个候选着法及对手应手 | 16 手 | 120 字 | 240 秒 |

每张模型卡下方的 **“发送 API 推理参数”** 控制是否把当前强度写入模型请求：

| 语义档位 | OpenAI 兼容 `reasoning_effort` | Anthropic extended thinking | Anthropic `max_tokens` |
|---|---|---|---|
| 快速 | `low` | `budget_tokens: 1024` | 2048 |
| 标准 | `medium` | `budget_tokens: 2048` | 3072 |
| 深思 | `high` | `budget_tokens: 4096` | 5120 |

- 若 API 档位本身是标准 `reasoning_effort` 值（如 `minimal / low / medium / high / xhigh`），开启开关后会原样发送该值；其他档位按上表语义映射。`off / none` 等关闭档位不发送原生推理参数。
- OpenAI 协议模型默认自动发送推理参数；若所用网关不支持 `reasoning_effort` 并返回 400，关闭“发送 OpenAI 兼容推理参数”即可回退到仅提示词控制。Anthropic 的扩展思考开关默认关闭。
- 开启后需要模型/服务支持对应参数：例如 OpenAI 推理模型、DeepSeek 思考模式、支持 extended thinking 的 Claude。若服务返回不支持该参数的错误，请重新布阵并关闭该开关。
- 暂停/重置仍会立即中止请求；API Key 不会写入请求之外的状态或日志。

请求示例：

```json
{"model":"deepseek-chat","messages":[],"reasoning_effort":"high"}
```

```json
{"model":"claude-sonnet-4-20250514","thinking":{"type":"enabled","budget_tokens":4096},"max_tokens":5120}
```

参数说明参考：[DeepSeek 思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)、[OpenAI reasoning 指南](https://developers.openai.com/api/docs/guides/reasoning)、[Anthropic extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)。

```text

│ React 19 + Vite 8  │ ◀────────────────────▶ │ Express 5                │

                                                └──────┬───────┬──────┘
                                                       │       │
```

自动评测页通过 `/api/tournament/*` 连接独立的 `Tournament` 调度器。调度器为每一局创建自己的 `Arena` 实例，串行跑完所有两两对阵，再用纯函数 `computeStandings` 汇总胜平负与排名；它不共享观战棋桌的状态、密钥或 SSE 流。

锦标赛页通过 `/api/championship/*` 连接独立的 `Championship` 调度器，并通过 `/api/championship/qualifier/*` 连接独立的 `Qualifier` 调度器。`Qualifier` 先执行两组 5 人单循环（20 局），每组前二进入四号种子池；随后 `Championship` 接收 12 个直邀席位与 4 个晋级席位，执行 24 局小组单循环，计算前 2 名，再动态创建 QF/SF/决赛系列赛；八强、半决赛与决赛统一采用 6 局 3 分制（胜方 1 分、和局双方各 1 分，先到 3 分晋级）。每局同样创建独立 `Arena`。并发度可设为 1–8：入围赛按同轮无共享选手的波次并行，小组赛按无共享选手的批次并行，淘汰赛同轮系列赛并行，同一系列赛内部仍逐局进行。每局结束和终止/关闭前，赛程、积分、系列赛比分与运行配置会分别原子写入 `QualifierCheckpointStore`（`data/qualifier.json`）与 `ChampionshipCheckpointStore`（`data/championship.json`）；重启后先恢复为“中断待续”，再由对应 resume 接口从未完成的对局继续。主赛完赛、中止或异常时，同一快照会经 `ChampionshipArchiveStore` 写入 `data/championships.json`，供对局管理页的「锦标赛档案」回看。

棋盘观战页通过 `/api/tournament/games/:id`、`/api/championship/games/:id` 或 `/api/championship/qualifier/games/:id` 读取当前对局的棋盘快照。调度器只为“正在进行的对局”和“最近结束的一局”保留 `Arena` 画面，避免把整届赛事的棋盘都放在内存里；页面跟随赛事 SSE 的 revision 刷新快照。

对局管理页通过 `/api/history/*` 连接 `HistoryStore`，并通过 `/api/championship/archives` 读取 `ChampionshipArchiveStore`。每局结束由 `Arena` / `Tournament` / `Qualifier` / `Championship` 的回调写入 JSONL，管理页按需分页查询；锦标赛档案按届读取。回放不依赖服务端额外接口：前端从标准开局 FEN 开始逐手应用档案中的 UCCI 着法，预计算每个半回合的棋盘快照。存储和查询都不接触模型密钥。

模型库页通过 `/api/models/*` 连接 `ModelProfileStore`。模型对象持久化在本地 JSON，开局/评测请求只传 `profileId` 与思考强度覆盖，服务端解析出包含密钥的完整 `ModelSetup` 后再交给 `Arena`；公开接口只返回掩码。

## 规则说明

- 坐标：文件 `a`–`i` 从左到右，横排 `0`–`9` 从红方底线向上；红方先行。
- 使用标准 90 格棋盘与完整棋子走法。走完一步后若己方将帅被将军（包括将帅照面），该步非法。
- 无合法着法的一方判负；被将军为将死，否则为困毙，两者均判负。
- 自动终局优先级：将死/困毙 → 静态死局 → 三次重复 → 无进展死局 → 总手数达到 300 个半回合。
- 一旦触发终局，服务端立即停止后续模型调用并释放 API Key；前端显示胜方或“和局”、终局原因及完整棋谱，不提供继续落子的入口。
- **静态死局**：双方都已没有车、马、炮、兵/卒等进攻子力，只剩将帅与士、象时，任何一方都不可能将死对方，立即判和。这是保守判定，不穷举所有理论上的无胜和棋。
- **无进展死局**：连续 60 个回合（120 个半回合）没有吃子且没有兵卒推进，判和；兵卒推进或吃子会重置计数。
- 未实现官方竞赛规则中复杂的长将/长捉裁判。娱乐模型对局采用上述简化判定。

## 安全与限制

- 临时填写的 API Key 只在本进程内存中短暂使用；对局结束或重置时释放，不进入 SSE、日志或浏览器存储。但 Key 会由本机服务转发给你配置的模型服务商。
- 模型库中的 API Key 需要支持重复使用，因此以明文保存在本机 `data/models.json`（服务会尽量设为仅当前用户可读写）；HTTP 接口只返回 `keyConfigured` 与末四位掩码，完整密钥只由服务端在开局或查询思考档位时解析使用。请勿分享该文件或把服务直接暴露到公网。
- 默认只绑定回环地址。若部署到公网，请自行加 HTTPS、访问鉴权与限流，并确保模型 Key 的合规使用。
- 单进程、单棋桌、单自动评测、单入围赛、单锦标赛，无账户；观战对局与自动评测的进行中状态不持久化，重启会丢失，但入围赛与锦标赛会分别从 `data/qualifier.json`、`data/championship.json` 恢复断点。模型库会从 `data/models.json` 恢复，已归档历史对局会从 `data/history.jsonl` 恢复，历届锦标赛档案会从 `data/championships.json` 恢复。
- 入围赛与锦标赛断点文件为了断电续赛，必须包含参赛模型的接口配置和 API Key（明文 JSON，服务会尽量设为仅当前用户可读写）；它们不会通过 HTTP 返回，也不会进入 SSE、日志或历史档案。请像保护 `data/models.json` 一样保护 `data/qualifier.json` 与 `data/championship.json`；开始新一届会覆盖对应文件，正常完赛后会删除它。
- 锦标赛配置 22 个席位（12 个直邀席 + 10 个入围赛席位），单届常规上限 86 局真实模型对局（入围赛 20 局 + 主赛 24 局小组单循环 + 7 场淘汰赛系列赛 × 6 局），费用和耗时仍远高于自动评测；若小组排名完全相同触发加赛，局数会继续增加。淘汰赛按 6 局 3 分制判定（胜方 1 分、和局双方各 1 分，先到 3 分晋级）；双方小组排名也相同而触发加赛时，直到出现一局胜负为止；请求层异常局不判胜但占用局数，连续给不出合法着法的对局则直接判负，按胜负计入积分/系列赛。
- 历史档案以明文 JSONL 保存在本机 `data/`，包含模型名称、对局结果、着法和模型给出的理由，但不包含 API Key；如需迁移可直接复制文件，如需删除可通过管理页或直接删除该文件。模型库档案同样可复制或删除，但删除后需要重新录入密钥。锦标赛档案 `data/championships.json` 只含公开模型信息、积分、系列赛与逐局结果，不含 API Key 和完整棋谱，可安全备份或删除。
- 自动评测按对局顺序串行运行；入围赛与锦标赛可选 1–8 路并发（默认 4），并发越高越容易触发服务商限流。参赛模型数量、局数和淘汰赛加赛会直接放大耗时和 API 费用。
- 自动评测中某一局发生鉴权/网络等请求失败时，该局标记为异常并继续下一局；异常局不计入胜平负与积分，但会单独显示。模型连续给不出可解析或合法着法时则直接判负，记入对手胜场。
- 静态死局采用保守规则（仅检查双方是否还有进攻子力），不会穷举所有理论无胜局面；无进展判和按本项目规则执行。
- 思考强度同时作用于提示词和可选的原生 API 推理参数；所有 OpenAI 协议模型都可选择 `minimal / low / medium / high`，选择后默认按 `reasoning_effort` 原样发送（旧 quick/balanced/deep 会归一化为 low/medium/high）；Anthropic 使用扩展思考预算。API 参数是否可用取决于所选模型与服务。若服务拒绝推理参数，请关闭“发送 OpenAI 兼容推理参数”后重开。
- LLM 调用非流式，不展示逐 token 思考过程；每个回合结束后放弃对话上下文，下一回合重新提供完整局面。
- 模型 API 的具体可用性由厂商决定；不支持 Chat Completions 或 Messages 协议的服务无法直接接入。
- 发生网络/鉴权等请求错误时对局进入错误状态，不自动判负、不随机代走，可重试本回合；但模型连续耗尽重试仍给不出可解析或合法着法时，该方直接判负并正常归档。
